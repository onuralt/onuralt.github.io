Master Thesis

Generator-Based Framework for Automated Formal Verification of Parametrized RISC-V Cores

Automated ISA-level equivalence checking for configurable RISC-V processors.

Problem Definition

Hardware Generators Produce Core Families

A hardware generator is a parameterized processor description. It does not represent one fixed core; it can emit different RTL designs from different configurations.

Parameters Select Concrete Cores

Each θ is a configuration vector. It can encode ISA extensions, memory options, tracing signals, reset behavior, and implementation choices.

Each generated processor instance is depicted as H(θ).

Each Core Needs a Verification Harness

VH means verification harness. For every generated H(θ), a matching harness must connect the right signals, assumptions, assertions, and tool flow.

Manual Harness Creation Becomes the Bottleneck

Building a matching harness by hand for every generated core is the time-consuming part.

How can this be solved without giving up configurability?

Methodology

From θ to One Proof Obligation

A configuration vector θ collects the architectural choices that define one generated hardware implementation. The methodology uses that same θ for the verification environment, so the design under verification, the reference model, the formal interface, and the framework are matching instances rather than separately maintained setups.

The Equations Become This Instance

The generated verification instance Vθ is the composition of the wrapped RTL core and the wrapped golden model. RVAVF connects both to the generated assertion set and the formal backend, turning the abstract requirement into one proof problem.

RVFIC Exposes the Core Uniformly

RVFIC supplies the observation layer for that instance. A map describes where architectural signals live inside the DUV, and RVFIC generates the bind probe and wrapper that expose those signals through one RVFI-style interface. The framework can then ignore core-specific signal names and hierarchy.

RVGM Provides the ISA Reference

RVGM supplies the specification side. It maintains architectural state, applies the configuration-dependent transition function for each instruction, and emits RVFI-compatible reference events. This is why the comparison can be made at the architectural trace level instead of the microarchitectural signal level.

RVAVF Builds the Proof Flow

RVAVF is the orchestration layer. It generates the assertion modules, top-level harness, and formal verification flow around the RVFIC-wrapped DUV and RVGM reference. The result is the verification condition Vθ ⊨ Pθ: the generated instance satisfies the generated property set.

1. θ selects one hardware implementation Hθ = Gcore(θ)
2. The same θ produces matching verification instances gmθ = gm(θ) fiθ = fi(θ), vfθ = vf(θ)
3. Wrapped implementation and reference form Vθ Vθ = vfθ(fiθ(Hθ), fiθ(gmθ))
4. Correctness is checked as trace equivalence ∀k : τkcore = τkgm Vθ ⊨ Pθ

Evaluation

Open-Source RISC-V Cores

The evaluation covers PicoRV32, NERV, Ibex, and Hazard3. NERV and Ibex achieved broad proof coverage; PicoRV32 and Hazard3 exposed RVFI timing or semantic mismatches rather than functional bugs.

CVA6 was attempted but excluded because its RVFI ports did not match the expected signal semantics.

Contributions

RVFIC, RVGM, and RVAVF Form One Generated Environment

RVFIC generates the observation interface. RVGM generates synthesizable reference behavior. RVAVF generates assertions, the top-level harness, the formal workspace, and JasperGold scripts.

Together, these components generate a complete ISA-level formal verification environment from shared configuration parameters.

Embedded Robotics

Tennis Ball Detecting and Tracking Robot

A more playful build in my portfolio: a tracked robot that uses a smartphone camera stream, PC-side OpenCV processing, Bluetooth commands, Arduino control, and regulated battery power to detect and track a tennis ball.

System Flow

Camera Stream to Motor Control

The robot splits perception and motion across the phone, PC, and Arduino. The phone streams frames over LAN, the PC detects the ball by fitting a circle to the filtered mask, then uses the circle center and radius to decide steering and distance before sending motor commands to the Arduino.

01 Capture Phone acts as an IP camera and streams live frames over LAN.
02 Filter PC converts RGB to HSV and thresholds the green ball.
03 Measure OpenCV fits a circle to the mask, using center offset and radius.
04 Decide Offset sign sets left/right; circle radius estimates distance.
05 Transmit PC sends the movement command through the HC-05 Bluetooth link.
06 Control Arduino MEGA converts serial commands into motor-driver signals.
07 Drive The motor driver moves the tracked chassis toward the ball.
08 Power Three LiPo cells feed regulated rails for logic and drive electronics.

OpenCV Filtering

RGB Frame to HSV Mask

The vision code captures the camera frame, resizes it, converts the RGB image to HSV, and applies tuned lower and upper HSV thresholds. This separates the green tennis ball from the background so OpenCV can find the largest contour and calculate the ball center.

Distance Estimate

Circle Radius as Range

After thresholding, OpenCV fits a circle around the detected white ball region. As the robot gets closer, the fitted circle grows in the frame, so its radius becomes an approximate distance signal.

Steering Error

Center Offset Drives Turning

The horizontal distance between the circle center and the frame center tells the controller which direction to turn. The motors keep correcting left or right until that offset falls under a chosen threshold.

Working Robot

Vision Loop Becomes Physical Motion

In this run, the PC keeps reading the phone camera stream, extracts the ball position, and sends correction commands over Bluetooth. The robot turns and advances as the circle center and radius change from frame to frame.

Tracking Behavior

Continuous Corrections Keep the Ball Centered

The working behavior is not a single command. Each frame updates the steering error, the PC sends a new serial instruction, and the motors keep correcting until the ball is close enough to the center of the frame and its radius indicates the desired range.

Digital Circuit Design

From Silicon Layers to Working Adders

I used Cadence to design and simulate two digital adders: the hardware blocks that let a processor add binary numbers. The main development path follows a Manchester Carry Chain Adder from control logic to physical layout, then compares it with a completed Carry Skip Adder.

Workflow: schematic design, physical layout, extracted views, waveform simulation, delay markers, and calculator measurements for leakage, static power, total power, and dynamic capacitance.

Layout Basics

Colors Become Chip Layers

A VLSI layout is drawn as stacked mask layers. Diffusion regions form transistor terminals, polysilicon crosses them to create gates, metal layers route signals, and contacts or vias connect one layer to the next.

This clean layer map separates the drawing conventions: contacts connect device layers to Metal1, while square vias connect one metal layer to the next metal layer.
